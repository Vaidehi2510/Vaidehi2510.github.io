01 Patchsentry Untrusted code. Explicit execution boundaries. +

A pull-request QA engine and web workspace built around a security question: how do you inspect proposed code without handing it the privileges of the system reviewing it?

Focus
Application security & secure CI/CD
Stack
Node.js · Docker · GitHub Actions · Next.js · PostgreSQL
Source
QA-testbot + patchsentry-web

Separate code from privilege

A proposed change can alter tests, filenames and application behavior. The workflow separates privileged source preparation from execution, then runs configured tests in a container with no network, a read-only source mount, a non-root user and dropped Linux capabilities.

Process, memory and CPU limits bound the work. Archive extraction checks a SHA-256 attestation and rejects traversal, links and oversized source bundles before execution.

Bind trust to the revision

Evidence and human decisions refer to the exact commit being reviewed. A decision needs the matching revision, a planned check, an authorized responder and a reason; a previous commit’s approval cannot resolve a new change.

AI findings remain separate from deterministic test results. Optional local inference accepts loopback endpoints, rejects redirects and has no cloud fallback.

Keep accounts and runners scoped

The web workspace uses owner-scoped database queries, exact Origin checks, secure session cookies and persistent login rate limits. Project runner tokens are random, stored as hashes and invalidated on rotation.

An outbound connector executes a fixed reviewed command only after local enrollment. Its policy constrains the repository, preview origins, browsers, AI backend and budget. The public web server does not execute product PR code.

Check the failure paths

Repository tests exercise path traversal, symlink escape, stale revisions, credential filtering, cross-account access, token rotation and malformed reports. These are specific controls with inspectable implementation and test sources.

Deployment still depends on a trusted runner, configured suites and authorized integrations. AI review is not a security audit; report redaction is pattern-based, and the web beta does not yet provide email verification or password-recovery delivery.

Review and evaluation

Five specialist agents use bounded tool loops, citation checks, read-only repository access, and budget caps. The review tooling has 244 tests with 77.8% coverage. Local-model operation through Ollama or LM Studio has no cloud fallback.

Desktop and mobile browser checks include accessibility testing with axe-core. These accessibility checks are separate from security review and independent test evidence.

A separate cloud-native companion

A Java/Spring Boot companion service uses idempotent REST APIs, optimistic locking, Redis rate limiting, and SHA-256-hashed tokens. Docker and Kubernetes provide health probes and autoscaling from two to six pods.

Its 39 Testcontainers tests cover PostgreSQL, MongoDB, and Redis. This service is separate from the Node.js review engine and Next.js workspace.

02 AURORA Cyber-physical detection & event correlation +

A cyber-physical threat correlation prototype that connects network, physical-security, and intelligence events into evidence-linked alerts for analyst review.

Role
Builder
Context
DC Critical Ops Hackathon 2026
Stack
Python · FastAPI · SQLite · NetworkX · React

The security problem

A network scan, a badge anomaly, and a relevant intelligence report can look unrelated in separate tools. AURORA explores how to bring those signals together with enough context for an analyst to investigate.

Build a correlation pipeline

The engine normalizes events from SQLite and scores relationships using timing, location, semantic similarity, shared entities, anomaly support, and event compatibility. NetworkX groups connected events; gradient boosting and a rule score rank the resulting clusters.

Supporting historical records and event-level evidence travel with each alert, so the output can be inspected beyond its headline.

Connect analysis to an operator

A FastAPI backend serves a React dashboard with event, alert, map, and raw-data views. Optional AI analyst and voice integrations support follow-up questions. A separate vision prototype compares DINOv2 frame embeddings with a normal baseline and uses SAM to locate anomalies.

Test the prototype in context

The repository includes an offline test that checks whether the engine finds a simulated cluster. The dashboard distinguishes demo events from its live database mode.

This is a hackathon prototype with historical and simulated data. Its published vision results use synthetic demo frames; they are not a production detection benchmark.

Threat knowledge retrieval

For the DC Critical Ops Hackathon 2026, I worked on a 3,557-record threat knowledge base, including CISA KEV, ICS advisories, and MITRE ATT&CK for ICS. Embeddings and FAISS connect incoming signals to related threat context.

Prototype measurements recorded retrieval below 50 milliseconds and analyst briefs below 60 seconds. These measurements describe the retrieval prototype, rather than a production service guarantee.

03 Watchpost Private incident triage on Apple platforms +

A native incident-triage app that keeps analysis on the device. It connects local similarity search, explainable priority scores, and optional on-device AI briefs to Siri, Shortcuts, and Spotlight.

Role
Builder
Context
Local incident-response tooling
Stack
SwiftUI · SwiftData · App Intents · Foundation Models

Keep incident context close

Incident records can contain sensitive operational details. Watchpost explores a local alternative to cloud-assisted triage: store records on the device, find related incidents there, and produce the brief without a cloud inference service.

Make priority reproducible

A deterministic engine computes a 0–100 score from severity, recency, recurrence, threat indicators, and resolution state. Local embeddings and exact cosine similarity surface related incidents.

Apple Foundation Models can write the brief on supported devices. The priority always comes from the same rules, and a rules-based brief remains available when the model is unavailable.

Build reliable state boundaries

The interface, App Intents, and Spotlight share one main-actor repository and SwiftData store. Value snapshots carry incident information across concurrency boundaries, while model identifiers keep cached embeddings aligned with the embedding model.

Five intents support logging, triage, finding open incidents, resolution, and navigation.

Verify the core behavior

The repository includes tests for priority ordering, score bounds, recurrence, similarity, and repository behavior. It ships with 30 sample incidents for exploring the workflow.

This is an on-device triage project. It does not claim a deployed enterprise SOC integration or measured incident-response improvements.

04 WARBREAK Adversarial simulation & resilience analysis +

An exercise-planning prototype that turns a written plan into assumptions, risk scores, and dependency chains, then lets people explore how those assumptions behave under simulated pressure.

Role
Builder
Context
SCSP AI+ Expo 2026 · Wargaming Track
Stack
Python · FastAPI · Pydantic · Next.js · TypeScript

Make hidden dependencies visible

Resilience depends on assumptions about communication, infrastructure, coordination, and recovery. WARBREAK makes those assumptions explicit and traces how one failure can affect the rest of a plan.

Compile assumptions into evidence

The FOGLINE pipeline combines optional LLM extraction with a local qualitative evidence catalog. A deterministic fallback keeps extraction available when a provider fails.

Each assumption includes a source span, a seven-factor score breakdown, missing mitigations, monitoring indicators, validation questions, and fallback options.

Trace decisions through a simulation

An assumption graph feeds adversary, cascade, and post-exercise analysis. Turn resolution combines rule-based effects with generated responses, while six metrics expose different consequences of each decision.

The engineering focus is making risk, dependencies, and failure chains inspectable throughout the exercise.

Keep the scope explicit

Source tests cover fallback extraction, short plans, and the training-scope gate. The API labels the scores as rubric-based and exposes warnings when extraction falls back.

This is a fictional training simulation. Scores are not historical failure probabilities, and generated opponent estimates are not live threat intelligence.

05 DevFlow AI Exploring security checks in an AI development loop +

A Python prototype that connects generated code, model-assisted vulnerability review, remediation and GitLab merge requests. The experiment is about making security review a visible step in the development workflow.

Focus
AI-assisted secure development
Stack
Python · Flask · Anthropic SDK · GitLab API
Status
Exploratory prototype

Make findings part of the workflow

A dedicated review stage asks the model to inspect generated files for hardcoded secrets, injection, XSS and missing input validation. Findings include a file, issue, suggested fix and risk label.

For medium or high model-reported risk, a remediation stage rewrites the affected file and requests another scan. The Flask dashboard streams these stages and records run history.

Carry the context into review

The GitLab adapter creates a branch, commits generated files and opens a merge request. When model-reported risk remains elevated, the MR is marked for human review.

This creates an inspectable workflow record. A generated risk label remains an assessment to verify, rather than evidence that the code is safe.

Be precise about the prototype

The current tester writes test files but does not execute them. The deployment adapter opens merge requests; it does not implement an automatic merge operation. The webhook validates events but does not yet launch the pipeline.

Those boundaries matter when describing the system’s capabilities. Generating a check is different from running it and evaluating its evidence.

The next security gate

Invalid model output currently falls back to a low-risk result. The next hardening step is to block on missing or malformed analysis, run independent tests and static checks, and require verified results before treating remediation as successful.

Authenticated run controls and stronger webhook configuration are also needed before exposing this prototype as a service.

06zappipeScanner evidence → a repeatable CI security gate.+

A Python pipeline around OWASP ZAP that turns web and API findings into prioritized remediation work and an enforceable build decision.

Focus
DAST & vulnerability management
Stack
Python · OWASP ZAP · Docker · GitLab CI · Jenkins
Practice
Scan, prioritize, remediate, validate

From alert to actionable finding

Scans cover web applications and REST/GraphQL APIs. Results map to OWASP Top 10 (2021), 15+ CWEs, and computed CVSS v3.1 base scores. The pipeline deduplicates and risk-ranks findings, then exports Markdown, JSON, and SARIF with remediation guidance.

Make the gate deterministic

GitLab CI and Jenkins fail on high-severity findings. The gate takes the higher of the scanner and CVSS ratings, so a computed score never downgrades scanner severity. A real scan of the demo target found reflected XSS (CWE-79) among 12 findings and blocked the build.

Assist triage, retain evidence

Optional Claude-assisted triage writes risk and remediation notes with a deterministic offline fallback. Scanner evidence controls pass/fail; the model does not. SARIF output supports remediation tracking and fix validation.

Make it repeatable

Twelve automated tests use a captured ZAP report. Docker packages the scanner, with Terraform deployment work for AWS EC2 and S3.
